## Communities nav icon → Material `MdOutlineGroups`, with slide-in animation

Replaced the two-speech-bubble Communities glyph in
`client/src/components/AnimatedNavIcons.tsx` with Material Design's
`MdOutlineGroups`, and animated it so the two side figures slide in.

**Inlined the geometry rather than installing react-icons.** Two reasons, both
load-bearing:

1. `react-icons` is not a dependency and cannot be added in this environment.
2. More importantly, `<MdOutlineGroups />` renders as a **single `<path>`**, so
   there are no per-figure elements to animate. The animation requirement alone
   forces the inline split.

Getting the exact path data without installing: `npm pack react-icons` into
/tmp, extract `package/md/index.mjs`, regex the `MdOutlineGroups (props)` block.
(Material "Outline" icons are still **fill**-based — `fill="currentColor"`,
`stroke="none"` — not stroke-based like the lucide glyphs elsewhere in this
file.)

**Decomposing one path into three figures — the two traps:**

1. The centre figure's head and body are each an outer shape plus an inner
   shape wound the opposite way to punch a hole. Those pairs **must stay in the
   same `<path>`** or the holes fill in solid.
2. Subpaths after the first use **relative** moves, so each extracted group
   needs its own absolute start. Resolved the centre body's `m-7.76-2.78`
   → `M16.24 13.65`.

**Verification without being able to see the render:** reassembled the three
path strings (undoing that one substitution) and asserted byte-equality against
the string pulled from react-icons. Came back `True`, 8/8 subpaths preserved.
Far better than eyeballing a 627-character path.

**Animation:** left `x: [-9, 0]`, right `x: [9, 0]`, both `opacity: [0, 1]`;
centre only does `scale: [1, 1.06, 1]` so the eye has something static to
measure the moving figures against. Right is delayed 0.06s. Reduced-motion is
already handled by the existing `state` computation.

**Blast radius:** one edit covers every site, because `SavannaShell` renders
both navs via `<MobileNavIcon name={item.label}>` — bottom nav, desktop nav,
`CommunitiesPage` (16/20/24px) and `CommunityDetailPage` (28px). Did not touch
`SavannaShell` itself (nav is under the standing do-not-modify constraint).

**Test coupling:** `server/pwa.assets.test.ts` pinned the old
`frontBubbleVariants` / `backBubbleVariants` names and the old bubble `d`
string. Updated to assert the new variant names plus the two `x` offsets — the
split is what makes the animation possible, so it is worth pinning.

## Communities icon rendered shorter than its nav siblings → uniform 1.5× scale

Reported after the swap above: the glyph sat visibly shorter than Messages /
Shops / Stories in the bottom nav.

**Diagnosis technique worth reusing:** every icon in this file shares
`viewBox="0 0 24 24"` and is rendered at the same `size`, so element px size
tells you nothing. Compare each glyph's extent in **viewBox user-units**:
Stories rect 18u tall, Shops basket 16u, Messages ~13.5u, `MdOutlineGroups`
only **12u (Y 6–18)**. That is the whole bug — the glyph is 2:1 inside a square
box, so it carries ~6u of dead padding top and bottom.

**Fix:** wrapped the three figures in a plain
`<g transform="translate(12 12) scale(1.5) translate(-12 -12)">`, taking Y from
12u to 18u — matching Stories exactly.

**Uniform, not Y-only.** First attempt was `scale(1 1.5)`; user rejected it
immediately because it turned the heads into ellipses. Uniform 1.5 pushes the
glyph to X −6…30 (6u ≈ 5.75px at size 23) outside the viewBox, which is safe
only because `SavannaShell`'s inactive slot is `w-11` (44px) around a 23px icon
(~10.5px slack/side) and the active pill is `w-max` with `px-3`. The SVG
already had `overflow: visible`.

**Inescapable trade-off:** a 2:1 glyph scaled to fill a 4:3-ish slot is either
distorted or ~1.5× wider than its neighbours. Keeping the width _and_ hitting
the height requires redrawing the artwork, not transforming it.

**Use a plain `<g>`, not a `motion.g`,** for a static parent transform —
framer-motion owns `transform` on elements it controls, so a static scale would
otherwise have to be re-encoded in every child variant. SVG `transform`
composes fine with the children's CSS transforms, so the slide-in and pulse
animations still work unchanged.

## Communities nav icon: scale hacks abandoned, swapped to lucide `users` (3 silhouettes)

Three failed attempts with Material `MdOutlineGroups` before the real fix:

1. **Root cause (unchanged from earlier note):** `MdOutlineGroups` is only 12
   user-units tall (Y 6–18) inside a shared `viewBox="0 0 24 24"`, while siblings
   span 16–18 units. Comparing element pixel sizes tells you nothing — every icon
   gets the same `size` prop. **Always measure glyph extent in viewBox units.**
2. **Attempt A — Y-only scale `scale(1 1.5)`:** fixed height, user immediately
   noticed the aspect ratio was off (heads became ellipses).
3. **Attempt B — uniform `scale(1.5)`:** preserved the circles but made it ~1.5×
   wider than neighbours. User rejected: "its not working".
4. **Actual fix:** threw the glyph away and used lucide `users` — **the same icon
   set as every other glyph in the nav**. It spans Y 3–21 (18 units, matching
   Stories) so it needs _zero_ scale correction.

**Lesson (the important one):** when the goal is "make it match its neighbours",
that is a _glyph-selection_ problem, not a transform problem. Scaling a
mismatched glyph can only trade height against width or proportion; you cannot
win. Pick artwork from the same set instead. I burned three rounds of user
feedback before recognising this.

### Deriving the mirrored 3rd silhouette (lucide `users` has only 2)

Reflect every X about the centre line (`x => 24 - x`) **and flip each arc's sweep
flag (1 -> 0)**. The sweep flip is what turns a right-bulging arc into a
left-bulging one; skip it and the copy bulges back into the figure it should sit
beside. Then shift the full figure +3 on X so it stays centred
(`H6` -> `H9`, circle `cx 9` -> `cx 12`).

Verified analytically (no rasterizer on this box — no rsvg-convert/inkscape/
chromium): parsed the path commands in Python and confirmed endpoint symmetry,
left `X 2..5` ↔ right `X 19..22`, left `X 8..8` ↔ right `X 16..16`, both about
x = 12. Result spans X 2–22 / Y 3–21.

**Prefer a plain `<g transform=...>` over `motion.g` for static parent
transforms** — framer-motion owns `transform` on elements it controls, so a
static scale gets clobbered or must be re-encoded in every child variant.
(A moot point here since the final version needs no transform at all.)

### Follow-up 1: side silhouettes pushed 2.5 units clear of the centre

User: "move the silhouette on the left and right outwards a bit ... they are close
to the central silhouette". They were flush: gap 0, so at strokeWidth 2 the side
strokes actually _overlapped_ the centre head circle.

Shifted each side out by 2.5 units (left `-2.5`, right `+2.5`):
`sideHeadArc` 8 -> 5.5 / 16 -> 18.5 · `sideBodyArc` 2 -> -0.5 / 22 -> 24.5.
Mirror symmetry preserved (5.5 ↔ 18.5, -0.5 ↔ 24.5 about x=12). New gap 2.5 on
both head and body, symmetric.

**Why the gap was 0 in the first place:** lucide's `users` has a 3-unit gap
between the centre figure and the right partial one. My earlier "+3 on X" shift
of the centre figure to make room for the mirrored left silhouette consumed
exactly that gap. Adding a third silhouette to a two-figure design is not free —
either the gap goes or the glyph gets wider. I chose wider.

**Trade-off recorded in the source comment:** glyph is now 27 units wide incl.
stroke vs ~20 for neighbours (18 tall). `overflow: visible` is already set and
the nav slot is 44px around a 23px icon, so nothing clips. If it later reads too
wide, the correct fix is narrowing the centre body (`H9 -> H10`, `M19 -> M18`),
_not_ pulling the sides back in.

### Bug found while in there: dash arrays were ~4x too long

`strokeDasharray` was 40 for side arcs and 50 for the centre body, but the real
path lengths are **10.54** (head arcs), **7.27** (body arcs), **22.57** (centre
body). With a dash array much longer than the path, the stroke is already fully
drawn for ~80% of the tween, so the figure snaps into place instead of drawing
in — the whole point of the slide-in was mostly invisible.

Fixed: measured the lengths, added `HEAD_ARC_LEN = 11`, `BODY_ARC_LEN = 8`,
`CENTRE_BODY_LEN = 23` (rounded up so the path is fully covered at offset 0), and
turned `leftSideVariants`/`rightSideVariants` into `(len) => Variants` factories
so each path gets its own dash offset.

**Rule:** `strokeDasharray` must be ≈ the path length. Worth checking any time a
draw-in animation looks like it's popping rather than drawing.

Test needed no change — all six assertion strings survive (`leftSideVariants`,
`rightSideVariants`, `bodyArcVariants`, `x: [-3, 0]`, `x: [3, 0]`,
`fill="none" stroke="currentColor"`); grepped to confirm. `npx tsc --noEmit` clean.
