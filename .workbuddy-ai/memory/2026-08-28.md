## Manus auth removed → Supabase (P0-2 DONE)

### CRITICAL: Supabase token signing — dispatch on `alg`, never on config
Supabase issues access tokens under **two** schemes:
- **Legacy**: HS256 with the project's "JWT secret".
- **Current**: asymmetric, usually **ES256**, verified against
  `{SUPABASE_URL}/auth/v1/.well-known/jwks.json`.

Projects created after the signing-keys rollout use ES256 **while still showing the
legacy JWT secret in the dashboard**. The dashboard is NOT a reliable signal.
Verifying an ES256 token as HS256 **rejects every single user**.

This project (`mfffcdbpuzrmchhatqns`) publishes an ES256 key in its JWKS, so it is
on the asymmetric scheme. `verifySupabaseAccessToken()` in `server/_core/supabase.ts`
now reads `alg` from the token's protected header and routes to
`verifyAsymmetricToken()` (JWKS, via `createRemoteJWKSet`) or `verifyLegacyToken()`
(HS256, raw + base64-decoded secret bytes). `SUPABASE_JWKS_URL` overrides the
endpoint for tests.

### Architecture (the important bit)
The browser **never holds a Supabase token**. It hands the access token to
`auth.signIn` once; the server verifies it and mints a short-lived HttpOnly session
cookie (`app_session_id`). The refresh token is a separate HttpOnly cookie
(`savanna_refresh`) so logout can rotate+revoke it server-side. Nothing is readable
from JS. `users.openId` is namespaced `supabase:<uuid>`.

## "App is not loading" — port split-brain (real bug, fixed)

User reported a blank app with console errors. Diagnosis:

### The console noise was NOT ours
`contentscript.js` / `contentScript.js` / `evmAsk.js` MaxListenersExceededWarning,
`[PHANTOM] error getting provider injection options`, and the hundreds of
`Unchecked runtime.lastError: Could not establish connection` lines all come from
browser extensions (Phantom wallet). Ignore them.

### The real errors were two lines
```
GET http://localhost:3002/@vite/client net::ERR_CONNECTION_REFUSED
GET http://localhost:3002/src/main.tsx net::ERR_CONNECTION_REFUSED
```
The Savanna dev server had died; nothing was on 3002.

### Root cause of the flakiness: `isPortAvailable` only probed one address family
`server/_core/listen.ts` used bare `net.createServer().listen(port)`, which binds
`::`. On macOS that **succeeds even when another process owns `0.0.0.0:<port>`**,
because the binds land in different families. Result: a split brain where IPv4
clients hit the other app and IPv6 clients hit Savanna, and `localhost` resolves to
whichever the browser tries first. That is why the port seemed to move around.

Reproduced: Savanna claimed port 3000 while themaraba.ai (PID 28070) already held
IPv4:3000 — both LISTENing on 3000, different families.

Fix: probe `0.0.0.0` **and** `::` (with `exclusive: true`) and require both free.
Savanna now correctly skips 3000 and 3001 and lands on **3002**.

### Port map on this machine (other projects, not Savanna)
- 3000 — themaraba.ai (PID 28070, Vite, IPv4) — **CORRECTION: not Savanna**
- 3001 — a Next.js app ("framr", PID 61813, IPv6)
- 3002 — **Savanna**

Verified on 3002: `/` → title "Savanna — Connect, shop, learn", `/@vite/client` 200,
`/src/main.tsx` 200 (8939 B transformed), `/api/trpc/auth.me` → `{"json":null}`,
`/manifest.webmanifest` 200, and 0 `VITE_ANALYTICS` placeholders in dev HTML.

## Mobile chat search "cream instead of white" — fixed

User reported the mobile `Search chats or people` input on `/messages` rendered
with the same `#F6F5F5` cream as the chat-row avatars. Cause was a stale
`dist/public/assets/index-*.css` — the **source** `client/src/index.css` had
already been corrected, but the built CSS still contained the OLD
selector `:root:not(.dark) .savanna-app label:has(input[aria-label="Search chats or people"]):not(.savanna-mobile-chat-search) { background: #F6F5F5 !important; }`.

Mobile chat search now stays white in light mode via an explicit rule at
`client/src/index.css:2028`:
```css
:root:not(.dark) .savanna-app .savanna-mobile-messages-canvas .savanna-mobile-chat-search {
  background: #FFFFFF !important;
  background-color: #FFFFFF !important;
  border-color: #FFFFFF !important;
  box-shadow: none !important;
}
```

Lesson: when light-mode color tokens change (recent commits rewrote cream
surfaces as pure white), **rerun `npx pnpm build`** so the dist picks up the
new CSS. The dev server reloads automatically, but anything served from
`dist/public` (preview deploys, the production server) was lagging the source.

Rebuilt `dist/public/assets/index-BHlJPpvl.css` (202.8 kB); buggy selector
no longer present. Verified with Chrome headless on the rebuilt CSS — search
input renders white.

**Gotcha**: `:not(.classname)` on a `:has(...)` ancestor selector is fragile —
some browser version combinations drop the whole selector. Mobile surfaces
should always have their OWN explicit rule, never rely on `:not(:has)` to
exclude them from a generic cream group (that's exactly the historical bug a
code comment in `index.css:1108` warns about).

### User pushed back: "nothing changed why?"

I byte-sampled their 810×1802 screenshot with a hand-rolled PNG decoder (PIL
isn't installed). The search input at `y=372..396` is solidly white
(`(255,255,255)` everywhere except antialiased placeholder pixels around
`#5F6861`). The story circles above (`y=144..252`) are `(246,238,221)` cream.
So the screenshot they sent was already showing white.

The likeliest "nothing changed" is **stale PWA cache** — Safari iOS installs
the service worker as soon as you open the PWAction, and `client/public/
service-worker.js` was on `savanna-shell-v4` with a network-first fetch
strategy. After a source change that DOESN'T alter the CSS hash
(`index-BHlJPpvl.css` → `index-D4udaofa.css` here is a hash change, so OK;
but if a build's CSS content is identical, the hash is identical), a browser
with the old SW can serve a stale CSS response.

I bumped the SW cache name to `savanna-shell-v5`. On next page load the new
SW installs, calls `activate`, deletes the `v4` cache, and `clients.claim()`
takes over — so any cached CSS from the old SW session is evicted. If the
user still complains, the next step is to instruct them to clear site data
(Safari → Settings → Safari → Advanced → Website Data → Delete or via the
PWA install's "Storage" panel).
