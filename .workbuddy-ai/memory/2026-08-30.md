# 2026-08-30

## Firestore `permission-denied` on chat messages — root cause and fix

**Symptom:** user sends a message to another user; nothing appears. Console:
`[Firestore] Message listener failed FirebaseError: Missing or insufficient
permissions.` from `firebaseChat.ts:432` (`useFirebaseMessages` onSnapshot) and
two `[API Query Error]` entries from the `invalidateQueries` refetch at
`firebaseChat.ts:448`.

**Root cause (found with the emulator, not by reading code):**
`firestore.rules` had the messages read rule as:

```rules
allow read: if signedIn()
  && resource.data.memberIds is list          // <-- the killer
  && request.auth.uid in resource.data.memberIds;
```

Security rules are not filters: for a `list` query Firestore validates the rule
against the *query's constraints*, not the documents. It can prove
`uid in memberIds` from `where("memberIds", "array-contains", uid)`, but it
**cannot prove the standalone type test `memberIds is list`** from that same
constraint. The unprovable clause evaluates to false, so the thread is denied to
its own members.

Why it looked like "sending" was broken: writes are single-document, where rules
*do* see the real payload, so the send batch always succeeded. Only the read
path failed — so the message was in Firestore but never rendered.

**Bisection (emulator, real rules, real SDK), all other clauses held constant:**

| Variant | members' query |
|---|---|
| original (with `is list`) | DENIED (L199) |
| drop `is list` | PASS |
| `memberIds.hasAny([uid])` | PASS |
| `signedIn()` only | PASS |

Baseline passing proves the query shape itself is fine and that Firestore really
does understand `array-contains` → `in`.

**Fix:** removed `resource.data.memberIds is list` from the read rule only.
Safe because `in` against a non-list field is a type error, which denies anyway.
Left `is list` in place on the **create** rule, where it is provable and useful.

Deployed ruleset `e2f87eb3-e4ed-45ed-9ec5-b8ce29481f9e`, verified byte-identical
to the local file via the Firebase Rules REST API.

## Diagnostic tooling added

- **`scripts/firestore-rules-smoke.mjs`** — runs the real chat read/write paths
  against the real `firestore.rules` in the Firestore + Auth emulators. Each
  step is isolated, because a permission-denied on a `writeBatch` doesn't tell
  you which of the N documents was rejected. Also asserts non-members are
  denied reading a message **by document id** (a non-member's array-contains
  query returns zero rows and is allowed, so it proves nothing).
- **`npm run test:rules`** — `firebase emulators:exec` wrapper. Needs Java
  (present: Java 25) and downloads the emulator jar on first run.
- Added an `emulators` block to `firebase.json` (auth 9099, firestore 8099,
  `singleProjectMode: true`) so the smoke test runs with the repo's own config.
- **`server/pwa.assets.test.ts`** — new test pins that the message read rule
  contains `request.auth.uid in resource.data.memberIds` and **not** `is list`,
  and that the create rule still does. 71/71 tests pass.

**Reading the deployed ruleset without the console** (useful — proves whether
the server matches the file before you theorise):
`GET https://firebaserules.googleapis.com/v1/projects/{project}/releases/cloud.firestore`
then fetch the named ruleset. Needs a Bearer token; gcloud has no account here,
but the Firebase CLI's token is in `~/.config/configstore/firebase-tools.json`
(`tokens.access_token`, refreshable via the CLI's public OAuth client).
