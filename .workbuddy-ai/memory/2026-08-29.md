### The bug (caused by my own earlier change)

Converting `vite.config.ts` to the function form `defineConfig(({ mode }) => …)`
made its **default export a function**. `server/_core/vite.ts` did
`createViteServer({ ...viteConfig })` — spreading a function yields `{}`, so
`root`, `publicDir`, `resolve.alias` and `envDir` were silently dropped in dev.

Symptoms (all quiet, nothing in the logs):
- `client/public` not served → `/manifest.webmanifest`, `/service-worker.js`,
  `/icons/*.svg` all fell through to the SPA index.html
- every `@/…` and `@shared/…` import failed to resolve

Fix: added `resolveViteConfig()` which awaits the function form when the export
is callable, and merged `server` options (`{...baseConfig.server, ...serverOptions}`)
instead of replacing them — replacing also silently disabled `fs.strict` and
`fs.deny`. Guarded by a new `server/vite-config.test.ts`.

**Lesson:** when `vite.config.ts` is the function form, anything importing it
directly (rather than letting the Vite CLI resolve it) must call it first. A
spread of a function fails silently.

| `CoursePage`, `LearnPage`, `CreatorStudioPage` | no | Learn is hidden; routes redirect to `/shops`; `CreatorStudioPage` is not routed at all |
| `PaymentsPage`, `PaymentDetailPage` | no | routed but **zero inbound links** anywhere in the app |

### Firebase doc ids are strings

The old page did `Number(params?.subjectId)` — meaningless for a Firestore id.
`subjectId` is now the raw string.

### Firestore rules would have blocked the write

`match /orders/{orderId}` originally had `allow update: if ... storefrontOwnerUserId
== request.auth.uid` — **seller only**. A buyer recording their payment choice
would have been denied. Added a second, tightly scoped branch:

```
resource.data.buyerUserId == request.auth.uid
&& resource.data.status == 'awaiting_payment'
&& request.resource.data.diff(resource.data).affectedKeys()
    .hasOnly(['paymentCountryCode', 'paymentProviderCode', 'updatedAt'])
```

Both guards matter: the `status` check stops a buyer re-confirming an already
paid order, and `affectedKeys().hasOnly()` stops them setting `status: "paid"`
for free (self-approval). Without the latter this is a real
privilege-escalation hole, not just a UX bug.

### Honest no-payments design

Launch is without payments, so checkout deliberately does **not** fake a charge
or move the order out of `awaiting_payment`. It records *how* the buyer intends
to pay (saved so the charge can be raised later without re-asking) and tells
them plainly that the seller will arrange payment directly.

## Glass composer, pill radius, circular actions, rotated send icon

### One shared field class instead of parallel rules

Both breakpoints now render `savanna-composer-field` on the field container, so
web and mobile literally cannot drift. Before this the radius was applied only
inside `@media (min-width: 1024px)` for `.savanna-desktop-composer > div`, which
is why mobile never got the pill.

The Tailwind `bg-[#f4f0e8] dark:bg-[#2a2119]` utilities were removed from the
mobile field — CSS owns that surface now, and a utility would fight the glass.

### Three opaque rules had to be deleted, not overridden

Same lesson as the glass header: an opaque background defeats `backdrop-filter`,
and the existing rules were higher specificity, so `!important` would have been
a losing fight. Removed the composer selectors from:

- the light cream search group (`.savanna-desktop-composer > div`,
  `.savanna-mobile-composer-field`)
- the dark desktop surface group (`.savanna-desktop-composer > div`)
- the dark mobile field rule (`.savanna-mobile-composer-field`)

The chat **search** keeps its opaque cream/dark fill — only the composer is glass.

### Send icon rotation: the real problem was framer-motion

The rotation was already `transform: "rotate(-45deg)"` — verified present by
rendering to static markup. But it sat in the `style` of an `m.div`, and
**framer-motion owns and rewrites `transform` on elements it controls**, so it
survives SSR and can be clobbered on the client. That is almost certainly why the
user still saw a horizontal plane.

Fix: moved the rotation onto a plain `<span className="savanna-send-icon">`
wrapper that motion never touches, with `.savanna-app .savanna-send-icon
{ transform: rotate(-45deg) }` in CSS. Removed the inline transform.

Verified final markup:
`<span class="savanna-send-icon"><div class="inline-flex..."><svg style="...transform:none">`

Note: `-45deg` IS 45° anticlockwise in CSS (negative = counter-clockwise), which
turns Lucide's right-pointing `send-horizontal` into the conventional up-right
plane. Also makes the send animation's `x: [0,6,20,-20,0]` fly up-and-right in
screen space, which is the desired effect.

### How to probe rendered markup without jsdom

No jsdom or testing-library in this repo (and `pnpm add` is blocked), but
`react-dom/server`'s `renderToStaticMarkup` works fine in the `node` test
environment. Two gotchas:
- `tsconfig.json` has `"jsx": "preserve"`, so esbuild falls back to the classic
  transform and client TSX throws "React is not defined". Run the probe with a
  throwaway config that sets `esbuild: { jsx: "automatic" }`.
- The probe test must use `createElement`, not JSX, because `vitest.config.ts`
  only includes `server/**/*.test.ts` (not `.tsx`).

## Bottom-nav symmetry, send-icon rotation, gold focus halo

Three UI fixes, verified live at https://savanna-2caf0.web.app (66/66 tests,
tsc clean, build OK, dev server PID 51415 on :3002).

### 1. Bottom nav spacing (`client/src/components/SavannaShell.tsx`)

With 4 tabs (Messages/Shops/Orders/Profile) on a `w-[min(calc(100vw-1.5rem),430px)]`
track, the old `active ? "flex-none" : "flex-1"` + `px-4` + per-link `px-1`
produced unequal gaps. The active pill kept its content width while the other
three shared the rest, so with tab 1 active: 16px to the left edge but ~27px to
the first icon, and ~47px between icons. Mirror-image problem on tab 4.

Fix: `justify-evenly` on the nav, drop `px-4` and the per-link `px-1`, and make
every tab `flex-none`. `space-evenly` gives one gap value at both ends AND
between every pair, so whichever tab is active the rail is symmetric. It also
removes an overflow the old layout had below ~330px viewports.

**Constraint reminder:** the user's standing rule is "do not touch the new nav
and bottom nav". This was an explicit, narrow exception — spacing only. Colours,
sizes, radii, icons and the glass treatment were left untouched.

### 2. Send icon rotation (`client/src/index.css`)

`.savanna-app .savanna-send-icon` went from `rotate(-45deg)` to `rotate(-90deg)`
(a further quarter turn anticlockwise, now nose-up). Test assertion in
`server/pwa.assets.test.ts` updated to match.

### 3. Gold focus halo on search + chat inputs (`client/src/index.css`)

Two product-wide a11y rules paint a gold outline on every focused control:
- `:where(a, button, input, textarea, select):focus-visible` → `3px solid #F2C14E…`
- the `@media (max-width: 1023px)` block → `.savanna-app input:focus-visible { outline: 3px solid #F2C14E !important }`

On buttons that is intended; on a search pill or the composer it reads as a
stray gold halo. New rule zeroes it for `.savanna-route-search`,
`.savanna-desktop-chat-search`, `.savanna-mobile-chat-search` and
`.savanna-composer-field` inputs/textareas. `box-shadow: none` is required too
because shadcn's `Input` paints focus via `focus-visible:ring-[3px]`, not an
outline. Specificity 0-3-1 beats the `!important` mobile rule at 0-2-1.

Note: `/orders` has **no** search input at all, so nothing to fix there.

### New regression guard (66 tests, +1)

"keeps the gold focus halo off the search and message fields" — asserts both
gold rules still exist (so the guard fails loudly if they are rewritten), then
that a `:focus-visible` rule covering each of the four field classes sets

Gotcha: a comma-separated selector list is **one** CSS rule, so a
`:focus, :focus-visible` pair cannot be asserted as two rules by a simple

## Bottom nav spacing, revision 2 — `justify-evenly` → `justify-between`

Follow-up after the earlier symmetry fix. The user sent two more screenshots
(could not be viewed — this model does not support images) asking to **"move the
active first tab to the left and the active last tab to the right, make the space
less."**

Diagnosis: `justify-evenly` gave mathematically equal gaps *including both ends*,
so on a 430px track the active pill floated ~37px off the left edge, then a ~94px
hole opened before the next icon. Equal is not the same as anchored — the user
wanted the ends pinned, not the gaps uniform.

Fix in `client/src/components/SavannaShell.tsx` (mobile bottom nav only):
- `justify-evenly` → `justify-between` (ends become 0 free space)
- width cap `430px` → `380px` (tighter inter-icon gaps)
- added `px-2` (8px) so the end tabs don't touch the rounded rail edge

Result on a 390px viewport: track = 100vw − 1.5rem = 366px, inner = 350px.
Active "Messages" pill ≈ 115px + 3 × 44px = 247px → 3 gaps of ~34px, and both
end tabs sit 8px from the rail edge in every tab state.

Verification: `tsc --noEmit` clean, `vitest run` 66/66. Built CSS confirmed to
contain `justify-between{justify-content:space-between}` and
`.w-\[min\(calc\(100vw-1\.5rem\)\,380px\)\]{width:min(100vw - 1.5rem,380px)}`,
then re-confirmed on the deployed bundle at https://savanna-2caf0.web.app
(assets/index-Csy7q0Og.css). Deploy: 31 files, hosting + rules + indexes.

Rule of thumb: `space-evenly` = equal gaps *including* the ends;
`space-between` = zero at the ends, all slack in the middle. For a floating pill
rail where an end tab can expand, `space-between` + a small inset is the right
choice — "equal" and "anchored" are different requirements.

Open question for the user: whether 8px (`px-2`) is the right end inset, or
whether they want it flush (`px-1` / 4px) or wider.

## Bottom nav spacing, revision 3 — px-2 → px-1

After revision 2 (`justify-between`) the user said the active first tab still
had too much space on the left compared to the top/bottom. The screenshot at
`~/Desktop/Screenshot 2026-08-29 at 23.26.21.png` showed ~12-14px on the left
vs ~8px top/bottom.

Why geometric `px-2 = 8px` looked bigger on the sides than on top/bottom: the
rail has `rounded-[34px]` corners on a `h-[60px]` body, and the active pill
has `rounded-[28px]` corners. At y just below the rail's top corner (y≈10),
the pill's left outline sits at `nav_inset + 28 - sqrt(28² - 18²)` = inset +
6.6px visually. So an 8px nav inset reads as ~15px of "empty space" on the
side, even though top/bottom look exactly 8px.

Fix: `px-2` (8px) → `px-1` (4px). Geometric left edge of the active pill at
y=center is now 4px from the rail; the rounded corner then provides the rest
of the visual breathing room, ending up close to the ~8px top/bottom gap.

Verification: `vitest run server/pwa.assets.test.ts` 13/13, full suite 66/66.
Built CSS contains `px-1{padding-inline:calc(var(--spacing)*1)}`, JS bundle
contains `px-1 py-2` in the nav class string. Deployed 31 files to
https://savanna-2caf0.web.app (asset: `index-CQNzqZxC.css`).

Lesson: in glass/pill rails, **rounded corners inflate perceived edge
padding**. Either reduce the geometric inset to compensate, or shrink the
inner element's border-radius. Don't trust equal `px` and `py` to *look*
equal — measure what the eye sees.

## Bottom nav spacing, revision 4 — px-1 → px-0 (final)

User: "move them more". Dropped the last 4px. The rail now has **no**
horizontal inset: `px-0` alongside `py-2`.

Final geometry (`client/src/components/SavannaShell.tsx`, mobile bottom nav):
```
fixed bottom-[max(0.75rem,calc(env(safe-area-inset-bottom)+0.5rem))] left-1/2
z-50 flex h-[60px] w-[min(calc(100vw-1.5rem),380px)] items-center
justify-between rounded-[34px] px-0 py-2 backdrop-blur-xl lg:hidden
```
The active pill is flush with the rail at y=center; the rounded-[28px] pill
corner against the rounded-[34px] rail corner is the *only* thing providing

the ~8px `py-2` top/bottom gap.

all of them already exist in the sheet, the CSS hash stays identical across
deploys. Verify the **JS** bundle hash moved, not the CSS one, or you will
wrongly conclude the deploy was a no-op.

## ROOT CAUSE FOUND — bottom nav inset was locked at 16px by `!important`

After four rounds of "move them more" with no visible effect, the actual cause
turned out to be nowhere near the JSX.

`client/src/index.css` (~line 1904), inside the **mobile media query**:

```css
.savanna-app .savanna-mobile-bottom-nav {
  ...
  width: min(calc(100vw - 1.5rem), 430px) !important;
  padding-right: 1rem !important;
  padding-left: 1rem !important;
}
```

`!important` on a **longhand** (`padding-left`) beats a **non-important
shorthand** (`padding-inline`, which is what Tailwind's `px-*` emits) regardless
of specificity. So `px-2` → `px-1` → `px-0` on the element were **all no-ops**.
The rail rendered 16px of horizontal inset the entire time, and the `430px`
width also silently overrode the `380px` cap I had put in the JSX.

Fix: set the CSS rule to `0.5rem !important` (8px) so it matches the `py-2`
vertical gap, and synced the JSX (`px-2`, `430px`) so the source of truth
agrees with what actually renders. Both files now carry comments pointing at
each other, because the JSX value is decorative.

New regression guard in `server/pwa.assets.test.ts`: matches the
`.savanna-app .savanna-mobile-bottom-nav` rule out of the stylesheet and
asserts `padding-left/right: 0.5rem !important` **and** that `1rem !important`
is absent. The comment states plainly that the `px-2` in the JSX is a lie
without this rule.

Verification: `tsc --noEmit` clean, `vitest run` 66/66. Built CSS has
`padding-left:.5rem!important;padding-right:.5rem!important`. Deployed —
**CSS hash moved this time** (`index-C0dlASzM.css`), which is itself the proof
the earlier `px-*` edits had produced no CSS delta at all.

### Diagnostic rule to reuse
When a styling tweak produces **no visible change** and the class is definitely
in the DOM: grep the global stylesheet for the element's *semantic* class and
look for `!important`. A utility can be perfectly applied and still lose.
Corollary: **if the built CSS hash does not change after a "CSS" edit, the edit
changed nothing** — that is the cheapest possible signal, check it first.

### Also checked and cleared

is network-first for navigation, cache-first only for `/assets/` (content
hashed). `CACHE_NAME = "savanna-shell-v9"` and `WORKER_URL =
"/service-worker.js?v=9"` are in step — keep those numbers in sync.

## Back-arrow colour — the same `!important` trap, different element

Follow-up to the header-icon work. The user reported the back arrow still
wrong after video/phone/three-dot were fixed.

Cause: **three** dark-mode mobile rules in `client/src/index.css` pinned it by
`aria-label`, all with `!important`, so the JSX `dark:text-[#fff8ed]` never had
a chance:
- `.dark .savanna-app [aria-label="Back to chats"]` → `color: #AEBAC1`
- `.dark .savanna-app [aria-label="Back to chats"] svg` → `color: #AEBAC1`
- `.dark .savanna-app [aria-label="Back to chats"] svg` → `var(--chat-icon-muted)`

Fix was **subtractive**: dropped the back-arrow selector from all three muted
lists. Chose that over adding a fourth `!important` counter-rule because a new
`!important` colour rule would also have clobbered the `hover:` gold (an
`!important` base rule beats a non-important hover variant), and would have
added to the cascade war that already bit us on the bottom nav.

Also gave the back button the same `hover:text-[#a87820] dark:hover:text-[#D9A441]`
as its three neighbours, which it was missing.

All four header controls now share one class string in
`client/src/components/ConversationHeader.tsx`:
`size-10 ... rounded-full text-[#3d2d1a] hover:text-[#a87820] dark:text-[#fff8ed] dark:hover:text-[#D9A441]`

Verified: `tsc --noEmit` clean; built CSS contains **zero** occurrences of
`Back to chats` while the JS bundle still has one (the aria-label prop) — a
clean way to prove the override is gone without breaking the selector.
Deployed, CSS hash `index-aQ7OIFAG.css`.

**Reusable check**: when an element will not take a colour, grep the stylesheet
for its `aria-label`. This codebase targets several controls that way, and
those rules are invisible from the JSX.
